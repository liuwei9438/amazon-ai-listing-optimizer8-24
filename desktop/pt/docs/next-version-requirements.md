## 一、网页版 + 双模式 AI 自动化（需求登记 A）

下一版本需要同时支持两种工作模式，并新增网页版客户端。

### 模式 A：内置 GPT API 自动化

程序后台调用 GPT API，自动完成（登记原项，未实施）：

1. 商品理解
2. 官方分类候选检索
3. AI 分类匹配
4. SP-API 验证
5. 属性填充
6. 缺失属性检查
7. 分类结果缓存
8. 批量任务管理

主要用于大量商品的无人值守自动处理。

### 模式 B：ChatGPT Agent 操作

允许用户在 ChatGPT Work 等支持网页操作的环境中，登录网页版商品刊登
助手，通过自然语言发出任务指令。登记的示例指令：

- 「帮我把所有未分类商品匹配亚马逊上传分类。」
- 「检查所有分类失败的商品。」
- 「把低置信度商品重新分析一遍。」
- 「检查哪些商品缺少上传必填属性。」
- 「帮我对比两个分类哪个更合适。」

Agent 可以通过网页版界面或受控任务 API 完成操作，但**实际可用能力
必须经过环境与授权测试，不得假定所有 Agent 都能直接访问本地电脑或
内部系统**。

### 双模式统一要求（登记原文 9 条）

1. 两种模式共用同一个分类引擎。
2. 共用商品数据库和任务队列。
3. 共用官方验证与缓存结果。
4. Agent 不直接修改 SQLite 数据库。
5. 所有操作经过身份认证、权限检查和审计。
6. 各店铺的数据、授权和任务独立隔离。
7. 允许查看、暂停、继续和重试任务。
8. 高风险操作必须经过明确授权。
9. 不重复开发两套分类业务逻辑。

## 二、智赢 UI/UX 对比审计（需求登记 B）

下一版本同时安排 UI/UX 对比审计。目标不是复制智赢的代码或完整界面，
而是借鉴合理的操作流程，提高现有软件的效率与舒适度。

**重点对比的 9 个功能领域：**

1. 商品列表与筛选
2. 商品详情编辑
3. 批量编辑
4. 变体管理
5. 分类选择
6. 图片管理
7. 商品刊登
8. 上传任务管理
9. 失败重试与错误反馈

**每个功能领域记录 7 项：**

1. 智赢的实际操作步骤。
2. 当前软件的实际操作步骤。
3. 两者的点击次数和操作路径。
4. 当前软件存在的不合理之处。
5. 推荐采用的改进方式。
6. 是否涉及底层业务逻辑修改。
7. 修改风险及回归测试要求。

**铁律：没有实际操作证据的部分必须标记为「待对比」，禁止凭空声称
智赢具有某种交互优势。**

## 三、未来目标架构（登记原文）

```
桌面客户端 / 网页客户端 / ChatGPT Agent
        ↓
统一认证与任务 API
        ↓
商品管理服务
        ↓
Amazon AI Category Engine
        ↓
SP-API 官方验证与属性引擎
        ↓
统一数据库、缓存和任务系统
        ↓
亚马逊正式刊登模块
```

要求（登记原文）：

- 业务逻辑独立于 UI。
- 桌面端与网页端共用核心服务。
- 不重新开发现有 AI 商品理解模块。
- 不替换稳定的图片优化模块。
- 不修改现有采集插件稳定基线。
- 不破坏当前上传功能。
- 所有新增功能严格模块化。

## 四、当前架构中未来需抽离的业务接口（登记 C）

对照目标架构，识别 pt-phase1 当前实现里已经按「服务边界」写好、
以及将来需要从 main.py 抽离的接口。**只识别，不动手。**

### 已按服务边界就位的（pt-phase1 交付，可被三种客户端复用）

| 模块 | 已就位的服务边界 | 下一版本角色 |
|---|---|---|
| `pt/store.py` | 单写者 SQLite：PT 字典 / Schema 缓存 / 候选 / 分配 / 验证 / 任务，店铺×站点隔离，mock/live 验证分行 | 「统一数据库、缓存和任务系统」的核心；Agent 经任务 API 间接读写，**不直接开 SQLite**（统一要求 4） |
| `pt/spapi_client.py` | 四官方操作 + 三模式环境（direct/proxy/mock）+ 官方端点白名单 + 错误分类 + 限流/重试 | 「SP-API 官方验证与属性引擎」的传输底座；token_provider/代理由装配期注入，天然可搬到服务端进程 |
| `pt/material.py` | 只读取料（不 import main、不调 AI、不改源数据） | 「商品管理服务」对引擎的喂料适配层；网页版/Agent 复用同一份抽取逻辑 |
| `pt/candidates.py` | 三策略候选检索（只生成候选、不做最终选择、不落库） | 「Amazon AI Category Engine」的检索阶段；模式 A 的第 2 步 |

### 将来需要从 main.py 抽离的接口（登记，不在本轮动）

| 未来接口 | 现状位置 | 抽离理由 |
|---|---|---|
| 商品读取服务（原始行/opt/理解结果的只读视图） | main.py 内部数据结构 + `_TEMPLATE_FIELDS` | material.py 目前靠装配期注入 record；网页版/Agent 需要同源的读取 API |
| 理解结果服务 | analyzer/*（引擎已独立，入口在 main） | 模式 A 第 1 步「商品理解」要无人值守调度，入口需 API 化 |
| 分类决策服务（AI 匹配 + 置信度 + 人工接管） | 模块 5/6 待开发 | 模式 A 第 3 步；双模式共用（统一要求 1/9） |
| 官方验证与属性服务（SchemaLink 拉取、必填属性检查、缺失清单） | 模块 6 待开发 | 模式 A 第 4/5/6 步 |
| 任务队列 API（建/查/暂停/继续/重试，含审计日志） | `pt/store.py` 任务表已就位，缺对外 API 层 | 模式 B Agent 的唯一操作通道（统一要求 2/4/5/7） |
| 认证与权限（桌面/网页/Agent 三端统一） | wz-auth worker（账号体系已有）；桌面端本地无鉴权 | 「统一认证与任务 API」；Agent 权限须先过环境与授权测试 |
| 上传管道入口 | main.py 上传流程（冻结，未批不改） | 目标架构最后一环；仅抽接口不改行为 |

## 五、下一版本架构建议与模块依赖（登记 D）

依赖方向（箭头=依赖，自上而下单向，无环）：

```
桌面客户端 ─┐
网页客户端 ─┼→ 统一认证与任务 API → ┬→ 商品管理服务（含商品读取/理解结果）
ChatGPT    ─┘   （鉴权/审计/店铺隔离） │        ↓
 Agent                       │   Amazon AI Category Engine
（仅经任务 API，             │   （material → candidates → 匹配 → 人工接管）
  不碰 SQLite）              │        ↓
                             └→ SP-API 验证与属性引擎（spapi_client + 模块6）
                                      ↓
                          统一数据库/缓存/任务（pt.store）
                                      ↓
                              亚马逊正式刊登模块（现有上传，冻结）
```

建议要点（登记，未实施）：

1. **任务 API 是 Agent 的唯一入口**：ChatGPT Agent 的每个自然语言指令
   最终翻译成任务 API 调用（查询/建任务/暂停/继续/重试），鉴权+审计在
   API 层做，SQLite 只由服务进程单写者触碰。
2. **模式 A 复用 pt-phase1 全部模块**：8 项自动化里的 2/7/8 已有落点
   （candidates / pt.store 缓存 / pt.store 任务表），1 复用现有理解引擎，
   3/4/5/6 是模块 5/6 的自然延伸——双模式不出现第二套业务逻辑。
3. **网页版先做只读视图再接管操作**：商品列表/筛选/任务进度是低风险
   只读面（对应智赢对比领域 1/8/9），编辑与刊登操作后置并逐项过授权。
4. **环境与授权测试先行**：模式 B 的能力边界（能否过 Cloudflare、能否
   持有会话、能调用哪些 API）必须在开发前实测，结论回填本文档，
   未测项目一律标「待对比/待测试」。
5. **Mock/Live 隔离纪律延续**：下一版本一切新接口沿用本阶段
   build_environment 信任模型与 verified_against 分行规则。
